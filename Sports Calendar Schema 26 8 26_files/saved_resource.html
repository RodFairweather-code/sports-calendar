Sports Calendar Schema

A relational schema for the Sports Broadcasting Calendar app, derived from the sixteen localStorage keys the app already reads and writes today — grouped into five domains, with an entity map and full column reference for each.

Source app Sports Broadcasting Calendar v3.03 Basis current localStorage read/write sites, verified against source Engine PostgreSQL

Why PostgreSQL

The app's sixteen localStorage keys already behave like a normalized relational schema — flat JSON blobs keyed by id, cross-referenced by other blobs via string ids (event_id, platform_id, pattern_id...). Every view assembles its data by parsing three or four of these keys and joining them in JavaScript at render time. A relational engine turns that implicit, hand-rolled join logic into real foreign keys and query joins.

The closed-vocabulary fields scattered through the app — decision states (Y/P/blank), rights (Y/N/unknown), booking status (confirmed/offered/unbooked) — become real CHECK constraints or enums instead of untyped strings, and multi-table writes (an editorial decision plus its default pattern, an event plus its cascade of bookings) become atomic transactions instead of sequential setItem calls with no rollback.

Engine PostgreSQL Deep, mostly-fixed relational structure with a few genuinely open-ended fields (staff capability tags) — a good fit for relational tables plus a narrow JSONB escape hatch, not a document store.
Shape 19 tables / 5 domains Scheduling, Editorial & Rights, Production Planning, Staffing, Bookable Assets — mirrors the app's own nav sections closely.
Migration path Seed files → seed scripts seedStaff.js, seedRights.js, seedPatterns.js and seedBookableAssets.js are already hand-maintained fixture snapshots — they map directly onto DB seed/migration scripts.

Bookable assets 2 tables

The simplest domain, and the one worth changing on the way in: asset_bookings today carries free-text production / programme fields but no foreign key to the event it's actually for. Adding a nullable event_id would let a booking optionally tie back to the calendar without forcing every booking to have one.

Worth deciding before this goes live
  1. Concurrent editing. localStorage is implicitly single-user — moving to a shared database makes concurrent edits possible, but a schema alone doesn't make them safe. Two producers opening the same event's staff booking at once will race. Decide on optimistic locking (a version column plus a conditional update) or a realtime layer before more than one person edits at a time.
  2. The "unsafe" admin bulk tools. Admin's hidden power-tools bar (Snapshot, Clear TAMS, Init All, Select/Clear Many Events) currently mutates localStorage directly and in bulk. Against a real database those need to become gated, logged operations — not raw table wipes — or they'll take out other people's in-progress work.
  3. Fixture sync identity. Three fixture sources (bundled JSON, TheSportsDB, fixturedownload.com) can describe the same real-world match. external_source + external_id on events is enough to store where a row came from, but de-duplicating across sources on re-sync still needs an explicit matching rule (kick-off time + team names is the obvious first pass).
